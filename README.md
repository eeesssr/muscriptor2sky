# muscriptor2sky

**MIDI → 光遇 15 键琴谱** 转换器，输出 **SkyStudio 兼容**的 `.txt` 格式，也能反向把琴谱还原成 MIDI。

接受任何标准 MIDI：DAW 导出的工程、手写谱、[MuScriptor](https://huggingface.co/MuScriptor/muscriptor-small)/MT3 等音频转谱模型的输出都可以。生成的谱子能被 SkyStudio 及一系列兼容它的光遇弹琴工具直接读取播放。

- **兼容 SkyStudio**：按 SkyStudio 的琴谱规范输出（UTF-16LE + BOM 的 JSON），这是光遇谱面的事实标准
- **零依赖**：只用 Python 标准库，不需要 `pip install` 任何东西
- **自动定调**：识别原曲的大调，头部写 `pitchLevel`，**保住原本的音高**
- **黑键智能吸附**：就近吸附，同一音级全局统一方向
- **自带校验**：`--verify` 按 SkyStudio 格式规范回读自检，确保 APP 能播
- **双向转换**：琴谱也能转回 MIDI，方便核对别人的谱子

## 安装

需要 **Python 3.8+**。克隆后即可使用，无需安装依赖：

```bash
git clone https://github.com/eeesssr/muscriptor2sky.git
cd muscriptor2sky
```

也可以装成命令行工具：

```bash
pip install -e .
muscriptor2sky --help
```

## 快速开始

### 命令行

```bash
# 最简：同目录生成同名 .txt
python -m muscriptor2sky song.mid

# 推荐：带曲名作者 + 自检
python -m muscriptor2sky song.mid -n "晴天" -a "周杰伦" --verify
```

### Windows 拖拽

把 `.mid` 文件拖到对应的 `.bat` 上松手即可。仓库提供三个，各管一件事：

| 文件 | 做什么 | 推荐度 |
|---|---|---|
| `转换-自动定调.bat` | 自动识别原曲大调，并让你选音区策略 | ⭐ 默认用这个 |
| `转换-手动定调.bat` | 手动指定 0~11，自动识别不准时兜底 | 备用 |
| `转换-虚音版.bat` | 用两键凑差音代替黑键（实验性） | 仅作研究，见[虚音说明](docs/虚音说明.md) |

三个模式共用一个核心，差别只在头部 `pitchLevel` 怎么写、以及是否补虚音键。
详见 [定调与 pitchLevel](docs/定调与pitchLevel.md)。

> 旧的 `转换.bat` 保留为 `转换-自动定调.bat` 的别名，已有快捷方式可继续用。

### Python API

```python
import types
from muscriptor2sky.core import read_midi, midi_to_sky, write_sky

args = types.SimpleNamespace(
    root=60, transpose="auto", grid=0.25, max_poly=0,
    name="晴天", author="", arranged=None, transcribed=None,
    bpm=None, bits_per_page=16, key="auto", encoding="utf-16",
)

m = read_midi("song.mid")
notes, info = midi_to_sky(m, args)
write_sky("song.txt", notes, args, info)
print(info["stat"])          # {'exact': .., 'octave': .., 'snapped': .., 'merged': .., 'dropped': ..}
print(info["key"])           # {'tonic': 11, 'name': 'B', 'hit': 0.982, 'confidence': 'high', ...}
print(info["pitch_level"])   # 11  ← 已写进头部
```

## 15 键与简谱对照

光遇的键名是 **0 基**编号，这一点最容易搞错：

| 文件里的 key | 键位 | 简谱 |
|---|---|---|
| `1Key0` … `1Key6` | 1–7 | `1 2 3 4 5 6 7` |
| `1Key7` … `1Key13` | 8–14 | `1' 2' 3' 4' 5' 6' 7'` |
| `1Key14` | 15 | `1''` |

对应 MIDI 音高：C4(60) D4 E4 F4 G4 A4 B4 · C5 D5 E5 F5 G5 A5 B5 · C6(84)。

> **键名约定依据 SkyStudio 谱面规范**：key 的数字部分是 **0 基**键位索引，
> 没有 `+1` 偏移，所以第一键是 `1Key0` 而不是 `1Key1`。
> 形如 `1Key5` / `2Key5` 的前缀数字不参与音高计算，两种写法指向同一个键。

| 字段 | 含义 | 怎样算好 |
|---|---|---|
| 移调 | 整体升降半音数 | 由调性决定；带 `★` 说明调性明确 |
| 精确 | 音高正好落在白键 | 越高越好 |

| 半音吸附 | 黑键吸到最近白键 | 越少越好，多了旋律会走样 |
| 同键合并 | 两音抢同一键，丢一个 | 少量正常 |
| 最大复音 | 同时按几个键 | **>4 手弹不了** |
| 可弹性 | 旋律能原样弹出的比例 | >95% 忠实 / <70% 建议换曲 |
| 定调 | 识别出的大调 | 带 `?` 表示调性模糊，建议手动指定 |

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-o, --out` | 同名 .txt | 输出路径 |
| `-n, --name` | MIDI 文件名 | 曲名 |
| `-a, --author` | 空 | 作者 |
| `--arranged` / `--transcribed` | 空 | arrangedBy / transcribedBy 字段 |
| `--bpm` | MIDI 速度 | 只影响 SkyStudio 编辑器格子显示，不影响播放 |
| `--bits-per-page` | 16 | SkyStudio 分页 |
| `--key` | `auto` | 定调：`auto` 自动识别 / `c` 强制 C 调 / `0`~`11` 手动指定 |
| `--register` | `auto` | 音区：`auto` 尽量贴近原曲音高 / `c` 固定落回 C4~C6 |
| `--pitch-level` | — | `--key` 的别名，兼容旧脚本 |
| `--encoding` | `utf-16` | `utf-16`（标准）或 `utf-8` |
| `--root` | 60 (C4) | 15 键里最低键的 MIDI 音高 |
| `--transpose` | `auto` | `auto` 自动移调 / `none` 保持原调 |
| `--grid` | 0.25 | 量化网格（拍），0 关闭 |
| `--max-poly` | 0 | 同时发音上限，0 不限 |
| `--verify` | 关 | 按 SkyStudio 谱面规范回读自检 |
| `--no-preview` | 关 | 不打印简谱预览 |

### 常用组合

```bash
# 手指弹不动的密集钢琴曲 → 限制复音
python -m muscriptor2sky song.mid --max-poly 3

# 只要主旋律，最容易弹
python -m muscriptor2sky song.mid --max-poly 1

# 有十六分音符，需要更细网格
python -m muscriptor2sky song.mid --grid 0.125

# 完全保留原始时间，不量化
python -m muscriptor2sky song.mid --grid 0

# 保持原调不移调（也不写 pitchLevel）
python -m muscriptor2sky song.mid --transpose none

# 强制写成 C 调（音高会被移调，但用默认乐器就能弹）
python -m muscriptor2sky song.mid --key c

# 手动指定调（自动识别不准时兜底）
python -m muscriptor2sky song.mid --key 7

# 换音域（从 A3 开始，共 15 键）
python -m muscriptor2sky song.mid --root 57
```

## 完整工作流：音频 → 琴谱

```bash
# 1) 用 MuScriptor 把音频转成 MIDI
#    关键：用 --instruments 只要钢琴轨，比事后删音干净得多
muscriptor transcribe --model medium --instruments "acoustic_piano" audio.wav -o piano.mid

# 2) 转成光遇琴谱
python -m muscriptor2sky piano.mid -n "曲名" -a "作者" --verify

# 3) 把 .txt 放到手机
#    Android: /sdcard/skyMusicAuto/   或用 APP 的文件选择器导入
```

MuScriptor 默认按**音色分组**分轨（每个 detected program 一轨，鼓单独一轨在 channel 9），
并不按"旋律/和弦/贝斯"分声部。转谱阶段用 `--instruments` 限定是最省事的做法。

## 工作原理

```
读取 MIDI（丢弃 channel 9 打击乐）
  ↓
识别大调：12 个音阶的音级覆盖率，用全部音符按时值加权 → pitchLevel
  ↓
定移调量的同余约束 t ≡ -K (mod 12)，再在 3 个八度内挑最不伤音域的八度
  ↓
（`--key c` 模式例外：不看调，直接按「实际被改动的音符比例」在 ±18 半音内穷举）
  ↓
超音域的音做八度折叠（只改八度，不改音名）
  ↓
黑键吸附最近白键（平局按和声协和度 → 旋律走向决定）
  ↓
同时刻同键合并（保留时值更长的）
  ↓
按 --grid 量化时间
  ↓
写 UTF-16LE+BOM 的 JSON
```

### 为什么移调要搜到 ±3 个八度

这是踩过的一个大坑，也是「转出来旋律丢了」的根因。

15 键只有 C4~C6 一个八度多一点。一首钢琴曲的旋律往往横跨 4 个八度，
注定有一部分音要八度折叠。**折叠本身不可怕，可怕的是折叠发生在旋律中段。**

如果整体移调选得偏高，旋律下半段还在键上、上半段全被折回低音区，
那条旋律线就会在中间被拦腰截断，听感就是「旋律没了」。

正确做法是**把整条旋律尽量整体放进 C4~C6**，只在真的放不下时才折叠
（也就是只在旋律两端折，不在中间折）。这靠的是移调量里那个 12 的倍数，
而这恰恰要求搜索范围能跨越八度。

旧实现把搜索范围写死成 `[-6, +6]`，根本表达不了「整体挪一个八度」，
于是只能靠音级统计挑一个「白键命中率高」的值，结果把大量音符挤出音域、
再逐个折叠。修复前后的实测对比（5 份真实 MuScriptor MIDI）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 旋律音完全正确 | 74.4% | **82.0%** |
| 八度缠绕（音对但音区错） | 16.8% | **9.0%** |
| 音级被改（弹错音） | 8.8% | 9.0% |

在 178 份社区谱面（[SkyAutoPlayerScript](https://github.com/StageGuard/SkyAutoPlayerScript)
的 shared_sheets，随机移到别的调后再转回 C 调）上的回环还原率：
旧实现 96.1%，新实现 **99.89%**。

### 自动定调：怎么在不改音高的前提下塞进 15 个白键

这是 v1.5.0 的核心改动，也是理解本工具的关键。

**矛盾在哪**：一首 B 大调的曲子，B 大调音阶里有 5 个音是钢琴黑键
（`1KeyN` 只有 15 个白键，物理上写不出来）。看上去只有两条路：

- 把黑键音吸附到白键 → 音高错了，旋律走样；
- 不允许 → 无解。

**实际解法**：谱面内容永远写成 C 大调形状，调性写在头部 `pitchLevel` 里。
所以只要整曲移调 `t ≡ -K (mod 12)`，原曲 K 大调音阶就**恰好**落成 C 大调形状，
一个黑键都不用碰。演奏时把乐器调到 K，按下的第 i 个键发出的就是原音高。

```
原曲：B 大调音阶   B  C# D# E  F# G# A#
移调 t = +1  ↓
谱面：C 大调音阶   C  D  E  F  G  A  B     ← 15 键，零黑键
头部：pitchLevel = 11 (B)                    ← 演奏时整台乐器升 11 半音
```

**注意 `pitchLevel` 会抬高整台键盘**（用游戏截图逐键核对过）：
演奏音高 = 15 键音高 + `pitchLevel`。所以声明 B 调之后，
实际发声的音域恒为 [60+11, 84+11] = B4~B6，与谱面写到哪个八度无关。

这一点决定了两件事：

1. **不能只写 `pitchLevel = K` 就完事** —— 还要选对谱面的八度，
   否则整曲会被平白抬高一个八度。
2. **`--key c` 也不是「音准」**：它把整曲移调 `t` 个半音，
   听起来调对了，但每个音的绝对音高都错了。

正确的八度选择目标在这里很容易搞错，我第一版就搞错了（详见更新日志）：
目标是**让演奏音高等于原曲音高**，而不是「折叠次数最少」。

实测（5 份真实 MIDI，「精对%」= 演奏音高正好等于原曲音高的比例）：

| 模式 | 精对% | 说明 |
|---|---|---|
| `--key auto`（修复后） | **76.2%** | 音高对，轮廓基本完整 |
| `--key auto`（修复前，有 bug） | 16.8% | 整曲被抬高约一个八度 |
| `--key c` | 0.0% | 整曲被平移，音高全错 |

force-C 是 0% 不是笔误：只要原曲不是 C 大调，整曲移调 `t` 就一定非零，
所有音的绝对音高都变了。旧版本一直是这样 —— 听起来「音都不是那个音」，
一半是黑键吸附问题，另一半就是这里。

**识别算法**：统计 12 个音级各占多少权重，对 12 个大调分别算音阶覆盖率，取最高。

**用什么音来判**：全部音符，按**时值加权**。这和移调量的取舍正好相反：
移调量必须只看旋律（低音会把移调拖偏），但调性判断问的是
「哪些音级在响、响了多久」，伴奏的低音和五度同样携带调性信息：

| 加权方式 | 准确率 |
|---|---|
| 旋律等权 | 95.51% |
| 全部音符按时值 | **97.19%** ← 采用 |

（不要按力度加权：SkyStudio 谱面格式没有力度字段，`vel` 恒为 1。）

**调性模糊怎么办**：15 键只有 7 个音级，五声音阶（大量流行/古风曲）只用 5 个。
同一个五声音阶可以同时被解读成好几个大调，覆盖率**数值完全相等** —
实测 178 份语料里有 14 份（7.9%）如此。这时按**终止式**裁决：
一首曲子的末音几乎总是主音（实测加「首音==主音」这一项反而降准确率，故未采用）。
再叠加「主音自身权重占比」和 Krumhansl-Kessler 弱先验打破残余平局。

**「几乎并列」的窗口**：命中率差距小于 0.5 个百分点时，这点差距远小于
「旋律 vs 伴奏」加权带来的抖动，拿它当证据是拿噪声当信号，所以交还给音乐先验裁决。
实测窗口取 0.005 不损失任何语料准确率，而真实 MIDI 上差别明显：

| 曲目 | 窗口=0 | 窗口=0.005 |
|---|---|---|
| 星降る海 | Eb | **Bb** |
| DAMIDAMI | Ab | **Eb** |
| 蝴蝶 | C | **G** |

后者都与 Krumhansl-Kessler 相关的偏好一致（DAMIDAMI 的 Eb r=0.637 远高于 Ab 的 0.445；
蝴蝶的 G r=0.914 远高于 C 的 0.660）。

验证（178 份社区谱面，每份遍历 12 个调 = 2136 个样本）：

| 指标 | 结果 |
|---|---|
| 12 分类准确率 | **97.19%**（2076/2136） |
| 完全判对的谱面 | **172 / 178** |
| 5 首真实 MIDI | **5 / 5** 判对（B、Bb、Eb、D、G） |
| 判错样本的实际损害 | **0 个可弹率下降**（错误样本的可弹率与原解完全相同） |

最后一行是关键：判错的全部是**真正歧义**的五声/无调性素材，
它们用另一个调来解，落白键的比例一模一样 —— 弹得出来，只是理论上「调」不同。

残余错误全部集中在**四度/五度关系调**（Δ=±5、±7，如 C↔G、B↔F#），
因为这两个调只差一个音级，音级不全的曲子数学上就区分不了；
Δ=±1、±6 则零错例。**理论上界约 98.4%**，不要按 100% 设验收线。

### 音区问题：pitchLevel 会把整台键盘抬高

这一点必须讲清楚，因为它有个绕不开的后果：

**演奏音高 = 15 键音高 + pitchLevel**（用游戏截图逐键核对过 4 个档位）。
而 15 键的物理排列固定是 C4~C6，所以：

```
pitchLevel = 0  ->  发声音域恒为 C4~C6
pitchLevel = 11 ->  发声音域恒为 B4~B6      ← 整曲高近一个八度
```

**这个音区改不了**：root 只决定「某个音高写到哪个键位」，不改变物理键的音高；
选哪个八度也只是让谱面写在不同位置，实际发声始终是 [60+pitchLevel, 84+pitchLevel]。

所以对 K 很大的曲子（B 大调 K=11），自动定调必然把整曲抬高。这不是 bug，
是 `pitchLevel` 语义的直接后果 —— 但听感上确实可能不如 C 调版。

两种取向都提供了：

| 参数 | 行为 | 适合 |
|---|---|---|
| `--register auto`（默认） | 保音高，接受音区被抬高 | 有对应调的乐器 |
| `--register c` | 放弃音高，落回 C4~C6 | 只想用默认乐器直接弹 |

```bash
python -m muscriptor2sky song.mid                    # 默认：保音高
python -m muscriptor2sky song.mid --register c       # 落回 C4~C6
```

实测 5 份真实 MIDI 的平均偏差（越小越接近原曲）：

| 曲子 | K | `--register auto` | `--register c` |
|---|---|---|---|
| Flower Dance | 11 | 3.66 半音 | **2.27 半音** |
| 星降る海 | 10 | **1.07 半音** | 2.73 半音 |
| DAMIDAMI | 3 | 3.75 半音 | **2.94 半音** |
| 纯蓝 | 2 | 2.01 半音 | **1.85 半音** |
| 蝴蝶 | 7 | 4.80 半音 | **1.89 半音** |

> 说明：C 调版在 4/5 首上更贴近原曲，因为它可以把整曲均匀平移很小的一段；
> 自动调版受 `t ≡ -K (mod 12)` 约束，只能整段跳八度。所以「自动定调更准」
> 只在音区本来就合适时成立 —— 这也是为什么两个选项都保留。

识别不准时用 `--key N` 手动指定即可（`转换-手动定调.bat`）。

### 为什么黑键要统一吸附方向

15 键琴只有白键，遇到黑键音必须改成相邻白键。改成哪边？这里有两个选择：

- **逐音决定**：旋律上行就向上取，下行就向下取。单看一个音最贴近原音高。
- **全局统一**：每个黑键音级固定朝一个方向。

旧实现用的是第一种，会导致一个隐蔽但很伤听感的问题：**同一个音级在曲子里会落到不同的白键上**。

实测星降る海，C# 分别被映射到了 G、A、B 三个白键：

| | 源音级 | 输出白键 |
|---|---|---|
| 修复前 | C# | G / A / B（3 个） |
| 修复后 | C# | 固定 1 个 |

同一句旋律重奏时音名变了，听感就是「跑调」「变色」。这就是用户说的「像是音都不是那个音」。

现在改成全局统一：穷举 2⁵ = 32 种「每个黑键朝哪边」的组合，选音级轮廓最吻合的一组。
有趣的是，5 份真实 MIDI 和 178 份社区谱面**都独立收敛到同一个答案：全部向上取**。

顺带修了另一个 bug：旧实现从整个 15 键里挑「最协和」的白键，
`bass_pc` 一变就可能把 C#4(61) 吸到 E4(64)——跨过整个 D4，音级直接被改掉。
现在吸附候选限定为**最近的上下两个白键**。

## 常见问题

**Q: 播放出来整体低了一个音级？**
键名是 **0 基**，第一键是 `1Key0`。如果你手写琴谱用了 `1Key1` 开头，就会整体偏移。

**Q: skyR 能播，但 SkyStudio 报错 / 播放速度不对 / 音不对？**

这是 **SkyStudio 时间模型**的问题，不是编码也不是音高映射（v1.2 已修复）。

SkyStudio 读谱面后这样算每个音的播放延时：

```js
// 来源：SkyStudio 生态的开源实现 buildTimingModel / 播放循环
unit      = gcd(所有相邻 time 的间隔);   // 时间单位
sleepUnit = duration / unit;
实际延时   = sleepUnit * (60000 / bpm);   // 注意这里又乘了 bpm

// 代入：实际延时 = (duration / unit) * (60000 / bpm)
```

要让实际延时等于 duration（即**播放速度和原曲一致**），必须满足：

```
gcd(times) == 60000 / bpm        ← 铁律
```

两个推论，正好对应两种症状：

| 情况 | 结果 |
|---|---|
| gcd 退化成 1ms（bpm 除不尽，量化抖动） | SkyStudio **无法建立节拍网格 → 报错** |
| gcd != 60000/bpm（差 2/4 倍等） | **播放速度整体快慢若干倍** |

以 `bpm=117` 为例：一拍 512.8205ms，八分音符 256.41ms 取整后
256/257 交替，gcd 退化成 1ms。此时 skyR 按毫秒差直接计时，一切正常；
SkyStudio 则报错或变速——这就是「skyR 能播、SkyStudio 不行」的根源。

**修复方式（v1.2）**：

1. 把 bpm 归一到能整除 60000 的值（`grid_safe_bpm`），保证 `60000/bpm` 是整数毫秒；
2. 找出原曲最细音符，令 `cell = 该音符毫秒数`，把 bpm 设为 `60000/cell`；
3. 所有 `time` 都取 `cell` 的整数倍，并做**后验校准**：
   实测输出时间戳的 gcd，若与 `cell` 不等，就用 gcd 反推 bpm。

这样 `gcd(times) == 60000/bpm` 恒成立，速度和音高都正确。

CLI 会直接显示网格状态：

```
时间网格: 单位 1 拍 = 128 ms  [SkyStudio 兼容]
```

> **注意**：为了满足上面的等式，工具可能会把 bpm 改成 468、1760 这类值。
> 这是正常的——SkyStudio 的 bpm 同时充当「网格分辨率」，不等于原曲速度
> 才有问题。实际播放速度由 time 与 bpm 共同决定，两者已经对齐。

**Q: APP 显示"乐谱格式不受支持"（编码问题）？**
如果不是上面那种情况，就检查编码。用 `--verify` 让工具自检，不要手动改 txt 编码。

**Q: 旋律跑调明显？**

先看输出里的一行统计：

```
映射: 精确 N / 八度折叠 N / 半音吸附 N / 同键合并 N / 超复音丢弃 N
```

判断标准（v1.3 实测口径）：

| 现象 | 说明 | 怎么办 |
|---|---|---|
| 「半音吸附」占比高 | 原曲大量用黑键（半音化程度高），15 键琴**物理上弹不出来** | 见下方「乐器上限」 |
| 「八度折叠」占比高 | 旋律音域远超 C4~C6 | 通常已由自动移调优化；仍高说明旋律本身跨 4 个八度 |
| 两者都低但听着不对 | 多半是复音过密或节奏太碎 | 试 `--max-poly 3` 或 `--grid 0.125` |

**关于「乐器上限」（重要）**：光遇 15 键琴是 **C 大调纯白键**乐器。
任何旋律里只要出现黑键音（钢琴上的黑键），就必然被改成相邻白键，
这是乐器的固有限制，不是转换错误。

我们实测过一首半音化很重的曲子（Relaxu - 星降る海），它最好的 7 音自然音阶
只能覆盖 **68.3%** 的旋律音 —— 剩下 31.7% 无论怎么移调都避不开。
这类曲子换成谁来编排都一样会走音，属于选曲问题而非工具问题。

判断你自己的曲子属于哪种，最直接的是看输出里的 `[可弹性]` 那一行：

| 可弹性 | 判定 |
|---|---|
| > 95% | 忠实，直接用 |
| 85% ~ 95% | 有可闻改动 |
| 70% ~ 85% | 降期望 |
| < 70% | 建议换曲 |

也可以看「半音吸附」占源音符的比例：

- **< 5%**：调性音乐，转换基本忠实
- **5% ~ 15%**：有较多离调音，会有明显改动
- **> 15%**：半音化很强，建议换曲或接受改编

**Q: 换了 `--root` 或手动移调，会不会比自动选得好？**

可以试，但通常不会。自动移调（v1.3 起）在 ±3 个八度内穷举，评分直接对齐
「转换后有多少音符被改动」，实测在 178 份社区谱面上达到 99.89% 的还原率。
手工调音域很难超过它。真想换，用 `--root 57` 之类整八度移动即可。

**Q: 和弦太密弹不了？**
`--max-poly 3` 或 `--max-poly 1`。

**Q: 中文乱码（Windows）？**
PowerShell 里先执行 `$env:PYTHONIOENCODING='utf-8'`。
`转换.bat` 已处理编码，直接用即可。

**Q: 为什么 bpm 字段和实际听起来不一样？**
播放器按 `songNotes[].time` 的毫秒差计时，`bpm` 只用于 SkyStudio 编辑器显示格子。

**Q: `pitchLevel` 是什么？**

它是**这份谱面要在哪个调上演奏**，取值 0~11，直接索引
`['C','Db','D','Eb','E','F','F#','G','Ab','A','Bb','B']`
（0=C，2=D，7=G）。

谱面内容**始终写成 C 大调形状（do-re-mi）**，换调靠 `pitchLevel` 声明，
不是把音符改写成别的黑键。源码依据：Sky Music Nightly 写谱时
`pitchLevel: PITCHES.indexOf(pitch)`、读谱时 `pitch = PITCHES[pitchLevel]`，
可逆；而**音符索引的换算完全不查这个字段**。

**Q: 那为什么要自动识别它？**

因为识别对了，音高才对。整曲移调 `t ≡ -K (mod 12)` 让原曲音阶落成 C 大调形状，
演奏时用 K 调乐器补回来 —— 音级保真实测 100%（见上方「自动定调」）。

**Q: 自动识别判错了怎么办？**

`--key N`（或 `转换-手动定调.bat`）强制指定。判错基本只发生在
五声/无调性素材上 —— 这类素材本来就有多个等价解，用哪个调都能正常弹，
只是听起来「调」不同。实测所有判错样本里，可弹率下降的数量是 **0**。

另外，错误集中在四度/五度关系调（只差一个音级），Δ=±1、±6 零错例。

**Q: 我想换音区而不是换调？**
用 `--root`。三者（音区 / 移调 / 定调）区别见
[定调与 pitchLevel](docs/定调与pitchLevel.md)。

### v1.5.1 — 修八度选择错误 + 测试有效性审计

v1.5.0 上线后收到真实反馈：「Flower Dance 还是最开始定 C 调的版本好听」。
查下去发现是**八度选择选错了**，而且 v1.5.0 的验证方法本身是无效的。

**Bug**：`transpose_for_key` 用「出界音符数最少」当评分。对音域窄的曲子，
t=+1 和 t=-11 的出界数都是 0，于是按 `abs(t)` 选了 +1。
而 `pitchLevel = K` 会把整台键盘抬高 K 个半音，结果整曲被抬了一个八度。

修复：评分改为「主群整体偏离的八度数 → 主群占比 → |t|」三级排序。
实测精对率（演奏音高 == 原曲音高）：**16.8% → 76.2%**。

**验证方法的错误**（更值得记）：v1.5.0 声称「音级保真 100%」，但那是拿
`src_pitch`（工具内部已折叠、已减 transpose 的中间值）去比 `key + pitchLevel`，
得到的是恒等式 `pitchLevel ≡ -transpose`，必然成立 —— **循环论证**。
它只能证明算术自洽，证明不了音高正确。现在改用「构造已知音高的 MIDI，
跑完整流程，比对原始音高」这种不循环的方式。

**测试有效性审计**（对每个测试问：把实现改坏，它会失败吗）：

- 注入 7 个 bug 做变异测试，7/7 都被抓到（补了 1 个原本漏掉的：
  `beat_unit_ms` 返回 float 时没人发现）。
- 修掉 2 个**无效测试**：
  - `test_pitch_class_mapping_consistent_end_to_end` 用了自动定调，
    整曲被移到白键上，吸附分支根本没走到 —— 改成 `transpose=none` 并断言
    `snapped > 0`，确保真的覆盖目标分支。
  - `test_beat_unit_ms_is_integer` 只断言 `== 500`，`500.0 == 500` 也成立，
    抓不到类型错误 —— 补了 `isinstance(..., int)`。
- 新增 3 个回归测试，并验证它们**在旧的有 bug 实现下确实会失败**。

**新增 `--register`**：修完音高发现一个新问题 —— `pitchLevel = K` 会把整台
键盘抬高 K 个半音，发声音域恒为 [60+K, 84+K]，root 和八度都改不了。
对 B 大调（K=11）这种曲子，自动定调必然把整曲抬高近一个八度。

所以提供两种取向：`--register auto`（保音高）与 `--register c`（落回 C4~C6）。
实测 5 首真实 MIDI，C 调版在 4/5 首上更贴近原曲 —— 因为自动调受
`t ≡ -K (mod 12)` 约束，只能整段跳八度，而 C 调版可以均匀平移很小一段。
两个选项都保留，让用户按听感选。

顺带修了空 MIDI 输入时 CLI 崩溃（`info` 缺字段导致 KeyError）。
测试 66 → 73 个。

### v1.5.0 — 自动定调

这一版改的是一处**静默的音高错误**，不是新功能。

v1.4.0 及之前，输出恒为 `pitchLevel = 0`，于是整曲被移调到 C 大调形状。
只要原曲不是 C 大调，**每一个音的音级都变了**。实测 5 份真实 MIDI：

| 模式 | 音级保真（演奏音级 == 源音级）|
|---|---|
| `--key c`（旧行为） | 0.0% |
| `--key auto`（新默认） | **100.0%** |

- **新增自动定调**：`--key auto` 为默认。识别原曲大调 K，整曲移调
  `t ≡ -K (mod 12)`，让原曲音阶正好落成 C 大调形状（零黑键），
  头部写 `pitchLevel = K`。演奏时用 K 调乐器补回来。
- **手动定调降级为备用**：`--key 0-11`（或 `转换-手动定调.bat`），
  自动识别不准时兜底。`--pitch-level` 保留为别名。
- **`--key c` 保留旧行为**：强制写 C 调，音高会被移调，
  但保证用游戏默认 C 调乐器就能弹。
- **`.bat` 重排**：`转换-自动定调.bat`（默认）/ `转换-手动定调.bat` / `转换-虚音版.bat`，
  `转换.bat` 保留为自动定调的别名。旧的 `转换-C调默认.bat`、`转换-定调版.bat` 移除
  （用 `--key c` / `--key N` 即可）。

**识别算法**：12 个大调音阶的音级覆盖率，用**全部音符按时值加权**
（旋律等权 95.51% → 全部音符 97.19%）。并列时按终止式（末音）裁决，
并以 Krumhansl-Kessler 相关打破残余平局。「几乎并列」用 0.5 个百分点窗口判定。

**验证**：178 份社区谱面 × 12 调 = 2136 样本，准确率 **97.19%**，172/178 完全判对，
5 份真实 MIDI 全对；所有判错样本的可弹率与原解**完全相同**（即都是真歧义素材）。
新增测试 16 个（共 65 个）。

> **又一处纠正**：v1.4.0 的文档用「D 大调卡农 pitchLevel=2 且黑键率 0%」作论据，
> 那是**循环论证** —— 谱面格式只能命名 15 个白键，任何谱面的黑键率都是 0%。
> 正确论据是源码：Sky Music Nightly 写谱 `pitchLevel: PITCHES.indexOf(pitch)`、
> 读谱 `pitch = PITCHES[pitchLevel]`，而音符索引换算**不查该字段**。
> 结论方向没错，论据已换成源码。

### v1.4.0 — 三种输出模式

把三个用途分流成三条独立路径，避免「默认输出」被少数特殊场景拖累。

- **C 调默认**：`pitchLevel = 0`，乐谱写成 C 大调形状，用游戏默认乐器直接演奏。
- **定调版**：交互选 `pitchLevel = 0~11`，声明谱面要在哪个调上演奏。
  对应 CLI 的 `--pitch-level N`，现在它**真的写进头部字段**。
- **虚音版**：`--virtual-notes`，用两键凑差音代替黑键。
  **实验性** —— 数学上误差仅 5~6 音分，但实测差音比基音低 67~102 dB，会被完全掩蔽。
  保留此模式是为了把结论记录在案，详见 [虚音说明](docs/虚音说明.md)。

顺带新增 `[可弹性]` 指标：旋律中能用 15 键弹奏的比例，用来提前判断「这首歌适不适合」。

> **重要纠正**：v1.3.1 的文档曾断言「`pitchLevel` 与音高无关」，**那是错的**。
> 正确结论是：`pitchLevel` 表示谱面要在哪个调上演奏，而谱面内容恒定写成 C 大调形状。
> 论据见 [定调与 pitchLevel](docs/定调与pitchLevel.md) 的源码引用。
> （v1.4.0 当时用的是语料黑键率论证，那是循环论证，已在 v1.5.0 更正。）

> v1.5.0 起这三种模式分别对应 `--key c` / `--key N` / `--virtual-notes`，
> 对应的 `.bat` 也改了名字。

### v1.3.1 — 黑键吸附方向一致化

修了「听起来很奇怪，像是音都不是那个音」的第二个成因。

- **根因**：`snap()` 按旋律走向逐个决定黑键向上还是向下吸附，于是同一个音级
  在曲子里会落到不同的白键上。实测星降る海：C# 被映射到 G / A / B 三个白键。
- **修复**：新增 `pick_snap_directions()` 穷举 2⁵ 种方向组合；`snap()` 把方向排到
  排序键首位；吸附候选限定为最近上下两个白键。
- **效果**（同进程 A/B）：音级映射一致率 54.2% → **69.4%**，星降る海 58.3% → **83.3%**。
- 新增 `tests/test_snapdir.py`（7 个测试）。

### v1.3.0 — 旋律保真度修复

修了一个「转出来的琴谱旋律丢了」的严重问题。

- **根因**：移调量的搜索范围被写死成 `[-6, +6]` 半音，表达不了「整首挪一个八度」。
  于是为了音级统计好看，把大量音符挤出 C4~C6，再逐个八度折叠，
  旋律线在中间被反复截断。
- **修复**：搜索范围放宽到 `[-18, +18]`（3 个八度），评分改为直接对齐
  「转换后实际被改动的音符比例」（出界 + 黑键，等权），且只用旋律声部决策。
- **效果**（5 份真实 MuScriptor MIDI）：旋律音正确率 74.4% → **82.0%**，
  八度缠绕 16.8% → **9.0%**。
- **验证**（178 份社区谱面移位回环）：还原率 96.1% → **99.89%**。
- 新增 `tests/test_transpose.py`，锁定搜索范围、整体平移、等权评分等行为。

### v1.3.1 — 黑键吸附方向一致化

修了「听起来很奇怪，像是音都不是那个音」的第二个成因。

- **根因**：`snap()` 按旋律走向逐个决定黑键向上还是向下吸附，于是**同一个音级在曲子里会落到不同的白键上**。
  实测星降る海：C# 被映射到 G / A / B 三个不同白键，33.1% 的旋律音落在音级映射不一致的音级上。
  同一句旋律重奏时音名变了，听感就是「跑调 / 变色」。
- **第二个 bug**：`snap()` 原来从整个 15 键里按 `(距离, 协和度, 方向)` 排序取最小，
  `bass_pc` 一变就可能把 C#4(61) 吸到 E4(64) —— 跨过整个 D4，音级直接被改掉。
- **修复**：
  1. 新增 `pick_snap_directions()`，穷举 2⁵=32 种「每个黑键朝哪边」的组合，
     选音级轮廓最吻合的一组（5 份 MIDI 与 178 份社区谱面都独立收敛到「全部向上」）；
  2. `snap()` 把**方向**排到排序键第一位（优先于距离、协和度）；
  3. 吸附候选**限定为最近的上下两个白键**，不允许为了协和度跳到很远的键。
- **效果**（同进程 A/B，3 份可精确对齐的样本）：
  音级轮廓保真度 82.4% → **83.9%**，音级映射一致率 54.2% → **69.4%**；
  其中星降る海 单曲改善最明显：一致率 58.3% → **83.3%**。
- 新增 `tests/test_snapdir.py`（7 个测试），锁定方向优先、最近邻、音级一致性等不变式。
- 时间网格铁律不受影响，5 份样本速度偏差仍为 0.00%。
